# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & test

```pwsh
dotnet build src --configuration Release
dotnet run  --project src/SponsorCheck.Tests --configuration Release --no-build
dotnet build IntegrationTests --configuration Release
dotnet run  --project IntegrationTests/IntegrationTests --configuration Release --no-build
```

Filter to a single test (TUnit uses `--treenode-filter`, not `--filter`):

```pwsh
dotnet run --project src/SponsorCheck.Tests --configuration Release --no-build -- --treenode-filter '/*/*/GitHubSponsorsPlatformTests/LiveLookup'
```

Integration tests build `src` first by depending on `nugets/SponsorCheck.<version>.nupkg`, so always rebuild `src` after changing the bundler/verifier before running integration tests.

One case where rebuilding is not enough: putting a packed file (`build/SponsorCheck.targets`, a verifier template) back from a backup that keeps its old timestamp, as `mv` does. The file is then older than the nupkg, pack sees nothing to do, and the package goes on holding the edited copy. That is what breaking the targets on purpose to check a test and then restoring them does. `touch` the file, or delete the nupkg, before rebuilding.

`SponsorCheck.csproj` has `<GeneratePackageOnBuild>true</GeneratePackageOnBuild>`, so `dotnet build src -c Release` produces the nupkg at `nugets/`. Don't add a separate `dotnet pack` step.

## Setup wizard (SponsorCheck.Web)

`src/SponsorCheck.Web` is a Blazor WASM wizard (deployed to GitHub Pages at https://simoncropp.github.io/SponsorCheck/ by `.github/workflows/deploy-blazor.yml`; tests gate the deploy) that generates consumer/author configuration. The consumer flow can inspect a published nupkg client-side (`Services/NupkgParser` + `Services/PackageLookup`, api.nuget.org flat container via the [RemoteZip](https://github.com/Papyrine/RemoteZip) package — HTTP range requests fetch only the zip central directory plus the sidecar/targets files in one coalesced batch read, so package size doesn't matter; the 30 MB `MaxNupkgBytes` cap only bounds the full-download fallback when a server ignores Range) to pre-answer owner mode, platforms, and exemptions — the sidecar file names/formats it parses are pinned by `RepoContractTests.SidecarFileNamesMatchVerifierTemplates`. `src/SponsorCheck.Web.Tests` contains anti-rot tests (`RepoContractTests`) that compare the wizard's hardcoded names against `build/SponsorCheck.targets`, `EmbeddedTemplates/ConsumerVerifier*.targets`, `OverrideableCodes.cs`, and the diagnostic-code docs — adding or renaming metadata, properties, or SC codes fails those tests until the wizard models (`Models/Platform.cs`, `Models/OverrideInfo.cs`, `Models/ScCode.cs`, the generators) are updated to match. Run them with `dotnet run --project src/SponsorCheck.Web.Tests --configuration Release --no-build`.

The wizard serves its own subset woff2 faces from `wwwroot/fonts/` instead of naming system families, because Chromium shapes with HarfBuzz on every platform — a bundled font measures identically everywhere, a system font does not, and the differing advance widths re-wrap prose and change full-page screenshot heights. That is what lets the Windows-authored `ScreenSnapshotTests` PNG baselines hold on Linux CI. The `unicode-range` descriptors in `wwwroot/css/app.css` declare coverage and `RepoContractTests.ShippedFontsCoverRenderedText` fails if the wizard renders a character outside them (it would fall back to a system font), so adding such a glyph means rebuilding the woff2 and widening the range — see `contributing.md`. Don't replace the font stacks with system families, and don't drop the `document.fonts.ready` wait in `ScreenSnapshotTests.VerifyScreen`; the faces are `font-display: block`, so an early capture is blank.

The html half of each screen snapshot is pretty printed through Verify.AngleSharp (`HtmlPrettyPrint.All` in `ModuleInitializer`), which also strips Blazor's `<!--!-->` render markers — as comment nodes, and as literal text inside `<title>`, where they are parsed as raw text rather than a comment. `<pre>` content is left byte-for-byte alone by the formatter (Verify.AngleSharp 5.1.0+), so the generated snippet inside a code box stays faithful; don't reformat those blocks by hand, they are regenerated on every run.

Bundling the faces pins which outlines are used, not how they are measured, so three further `app.css` rules are load-bearing and were each needed before Linux matched Windows: `text-rendering: geometricPrecision` on `html, body` (rasterizers round advance widths onto their hinting grid differently, re-wrapping prose), an explicit `font-family` on `code, pre, kbd, samp` (the UA stylesheet's rule beats inheritance, so inline code silently uses the platform monospace), and `line-height: 1` on `code, kbd, samp` (a line box is the union of the strut and each inline box, placed from per-font ascent/descent that round differently per platform). They look cosmetic; deleting any one reintroduces per-OS PNG drift. `wwwroot/fonts/readme.md` records the reasoning.
The third flow is `Pages/Package.razor` (`/package/{PackageId}`, deep-link only, no Home card), meant to be linked from a package's own docs: it runs `PackageLookup.Inspect(id, null)` from `OnParametersSetAsync` keyed on the route value (with a load token, since the router reuses the instance across `/package/A` → `/package/B`), seeds a fresh `ConsumerModel` via `ApplyFacts`, and drops the situation step in owner mode because nothing is left to ask. It shares `FactsSummary`, `LicenseModeStep`, `CpmChoice` and `ConsumerOutputPanel` (`WizardUrl`) with the consumer flow. `LicenseModeStep` mutates the parent's model, and a DOM event handled in a child re-renders only the child, so every input there carries `@bind:after="NotifyChanged"` and the parent passes `Changed="StateHasChanged"` — drop one and the parent's Next button goes stale (`ConsumerPageTests.SponsorModeRequiresAccount` and `LicenseModeStepTests` guard it). `WizardLinks` owns the wizard urls. Tests never reach nuget.org: bunit tests register `StubNuGetHandler`, and the Playwright tests route `https://api.nuget.org/**` through `FakeNuGetFeed` before navigating (Playwright adds the CORS headers and answers the Range preflight itself). `MapFallbackToFile("index.html")` registers `{*path:nonfile}`, which 404s a dotted last segment such as `/package/Verify.Xunit`: the test host uses the `{*path}` overload for that reason (with `UseRouting()` placed after `UseStaticFiles()`, because the unconstrained pattern also matches asset urls and the static file middleware steps aside once routing has picked an endpoint), the Blazor dev server (`dotnet run`) still has the limitation, and GitHub Pages (404.html) does not.

## The two-stage MSBuild architecture

This is the central design. Hold it in mind when reading any file in `SponsorCheck/`.

**Stage 1 — Bundler (OSS-author pack time).** `BundleSponsorListTask` runs from `src/SponsorCheck/build/SponsorCheck.targets`, which is auto-imported into any project that PackageReferences `SponsorCheck`. It:

1. Reads `<Platform>Account` metadata from the author's `PackageReference Include="SponsorCheck"` (or matching `PackageVersion` under CPM).
2. Gets each enabled platform's account list: from the fetch shared across the build (see "The platform fetch is shared across a build"), from its own call to the platform's API when there is no shared result it can use, or from the `<SponsorListOverride>` JSON if set.
3. Writes eight files into the author's intermediate output, all packed into the produced nupkg:
   - `build/SponsorCheck.SponsorHashes.txt` — sorted, deduped `SHA256("{platform-id}:{lowercase(account)}")` hashes.
   - `build/SponsorCheck.PackDate.txt` — UTC date the package was packed (or `SponsorCheck_PackDateOverride` if set, used by integration tests).
   - `build/SponsorCheck.AuthorAccounts.txt` — `platformId={account}` lines for each enabled `<Platform>Account` on the author's SponsorCheck reference. Used by the verifier to construct platform sponsor URLs in the SC001/SC005 messages.
   - `build/SponsorCheck.SeverityOverrides.txt` — `SC001=warning` lines for the `OverrideableCodes` the author retuned, ordinal-sorted.
   - `build/SponsorCheck.MessageOverrides.json` — replacement message bodies for those same codes.
   - `build/SponsorCheck.LandingUrl.txt` — the author's `SponsorLandingUrl`, if set.
   - `build/SponsorCheck.Exemptions.json` — the `<SponsorExemption>` definitions, keyed by name.
   - `build/<ThePackageId>.targets` — the verifier targets file, generated by template substitution (see below).

   The last four data files are written unconditionally (empty, or `{}` for the JSON ones) so the verifier can read them without probing. A ninth, `build/<ThePackageId>.SponsorCheckInner.targets`, appears only in the own-targets case below.
4. Also packs the multi-targeted `tasks/{netstandard2.0,net472}/SponsorCheck.dll` (plus its closure of System.* deps from `bin/{Configuration}/{tfm}/`).

The `build/` prefix on those files is the default. When the author sets `CheckTransitiveReferences="true"` on the SponsorCheck reference, `SponsorCheck.targets` swaps the pack folder to `buildTransitive/` (via the `_SponsorCheck_BuildFolder` property). NuGet imports `build/<id>.targets` only for direct references but `buildTransitive/<id>.targets` for direct *and* transitive ones, so the folder choice is the direct-vs-transitive verification toggle — no verifier code change is involved. The `tasks/` DLLs stay put (referenced as `..\tasks\`, which resolves identically from either folder).

### Coexisting with a package that ships its own `<PackageId>.targets`

NuGet auto-imports exactly one file named `<PackageId>.targets`, and the verifier claims it. A package that *also* ships its own `<PackageId>.targets` (its own MSBuild build logic) would otherwise collide at pack — `NU5118` under `TreatWarningsAsErrors`, or a silently dropped verifier otherwise. `SponsorCheck.targets` handles this: before adding its own `<None>` items it scans `@(None)` for an author item landing in the `$(_SponsorCheck_BuildFolder)\$(PackageId).targets` slot — matching both a `PackagePath` that names the file and one that names only the folder (`buildTransitive\`, the more common authoring style, where the item's own file name puts it in the slot). If found, it relocates that item (via `Remove ... MatchOnMetadata="Identity;PackagePath"` + re-`Include`) to a `<PackageId>.SponsorCheckInner.targets` sidecar, and passes `InnerTargetsImportFileName` to the bundler. The bundler then replaces the `__SC_INNER_IMPORT__` placeholder (in both verifier templates) with an `<Import>` of that sidecar — so the verifier owns the auto-import slot while the author's own logic still loads in consumers. Matching on `Identity` as well as `PackagePath` is load-bearing once folder-form paths are matched: siblings packed to the same folder (a `<PackageId>.props`) share the `PackagePath` value and would otherwise be removed too.

`MatchOnMetadata="PackagePath"` alone was also why an author shipping to both `build/` and `buildTransitive/` used to keep the non-pack-folder copy — which meant direct consumers imported the author's `build/<id>.targets` and got no verifier at all. Now both copies are relocated and the verifier plus a full set of data sidecars is packed into *both* folders (`_SponsorCheck_SecondFolder` / `_SponsorCheck_PackSecondFolder`; the data `<None>`s batch over `@(_SponsorCheck_PackFolder)`). Each folder is self-contained because the verifier resolves its data files relative to `$(MSBuildThisFileDirectory)`, and the two verifier copies carry identical target names, so a consumer importing both is idempotent. This only happens when the author claimed the slot in the second folder — with no collision the verifier still lives in exactly one folder, which is what keeps `CheckTransitiveReferences` the direct-vs-transitive toggle. Regression coverage: `AuthorPackTests.OwnTargets_RelocatedToSidecar_NoCollision` / `_FolderFormPackagePath` (pack structure), `ConsumerBuildTests.DirectReference_ToPackageShippingItsOwnTargets_IsVerified` (the direct consumer actually verifies), and `BundleSponsorListTaskTests.InnerTargetsImport_*` (placeholder substitution).

**Stage 2 — Verifier (consumer build time).** When a consumer project PackageReferences ThePackage, NuGet auto-imports `build/<ThePackageId>.targets` (or `buildTransitive/<ThePackageId>.targets`) from the nupkg. That file `UsingTask`s the version-scoped verifier task (`VerifySponsorshipTask_<version>`, see below) from the bundled `tasks/` DLL and runs it `BeforeTargets="BeforeBuild"`. The verifier reads consumer-side license metadata (`SponsorshipLicenseIgnored`, `SponsorshipLicensedUntil`, `<Platform>SponsorAccount`, `SponsorshipStart`, `SponsorshipPrivateUntil`) and either passes, warns, or fails with an `SC0xx` code. It renders that diagnostic but does not log it — see "Diagnostics are announced once per build" below.

ThePackage acquires **no runtime dependency** on `SponsorCheck`. Everything ships embedded.

## Why template substitution (not `$(...)` expansion)

`ConsumerVerifier.targets` (in `SponsorCheck/EmbeddedTemplates/`) uses `__SC_PACKAGE_ID__` and `__SC_PACKAGE_ID_RAW__` as placeholders. The bundler substitutes them at pack time:

- `__SC_PACKAGE_ID__` → the package id with non-alphanumeric chars replaced by `_` (used in MSBuild target/item names — MSBuild rejects dots/dashes there).
- `__SC_PACKAGE_ID_RAW__` → the literal package id (used inside element values).
- `__SC_TASK_NAME__` → the version-scoped verifier task type (`VersionedTaskName.Verify`), used in both the `UsingTask TaskName` and the task element.

MSBuild target `Name` attributes do **not** support `$(Property)` expansion. That's the constraint forcing template substitution rather than dynamic property reads. Per-package unique target names (`_SponsorCheck_Verify_<sanitized-id>`) prevent collisions when a consumer references multiple SponsorCheck-using packages.

## Why the verifier task name carries the SponsorCheck version

MSBuild's task registry is keyed by **task name alone** — not assembly path, identity, or version — and the first `UsingTask` to claim a name serves every invocation of it in that project. Since every SponsorCheck-bundling package ships its own copy of `SponsorCheck.dll`, a bare shared name meant one copy ran *all* the verifiers in a consumer project. The moment two such packages bundled SponsorCheck versions with different task APIs, the build died with `MSB4064: The "<X>" parameter is not supported by the "VerifySponsorshipTask" task` — pointing at the *newer* package's targets while naming the *older* package's DLL path. (Giving each release a distinct `AssemblyVersion` does not help: registration is resolved before assembly identity is consulted.)

So `SponsorCheck.csproj`'s `_SponsorCheck_GenerateVersionedTaskName` target emits `VerifySponsorshipTask_<version>` — a subclass of `VerifySponsorshipTask` (which is therefore *not* sealed) — plus a `VersionedTaskName.Verify` constant initialized with `nameof`, so the bundler's `__SC_TASK_NAME__` substitution can't drift from the type actually compiled. Each release lands in its own registry slot, so version-skewed packages coexist. `$(Version)` feeds the name, with `.`/`-`/`+` sanitized to `_` so prerelease versions stay valid identifiers.

Consequences worth knowing: `VerifySponsorshipTask` must stay unsealed and stay the direct base of exactly one generated type, and packages published before this change still register the bare name — harmlessly, since it no longer collides with anything newer.

Regression coverage: `AuthorPackTests.BundledTargetsScopeTaskNameToSponsorCheckVersion` (the packed verifier binds a scoped name and no bare one) and `BundleSponsorListTaskTests.TemplateSubstitution_BindsVersionScopedTaskName` (the named type exists, derives from the task, and reaches the rendered targets).

## Diagnostics are announced once per build

The verifier runs in every project that references ThePackage, and again in every inner build of a multi-targeted one, so a diagnostic used to repeat once per (project, target framework) pair. It is still *rendered* there; it is *reported* once per build.

Both generated templates pass `DeferDiagnostic="true"`. Verification is unchanged, but instead of logging, whatever the run would have logged is captured and handed back through the `Diagnostic*` outputs. The capture is a `TaskLoggingHelper` over `CapturingBuildEngine` — which is why `DecisionApplier` and the dozen message renderers below it needed no sink threaded through them, and why the deferred and immediate paths render byte-identical text. The verify target then `<MSBuild>`-calls `_SponsorCheck_Announce_<sanitized-id>` **in the same targets file**, passing the rendered diagnostic as global properties; that target runs the same task in announce mode (`AnnounceCode`/`AnnounceSeverity`/`AnnouncePayload`), which logs it.

The dedupe is MSBuild's own build-result cache. Results are keyed by (project path, global properties, targets) and the cache lives in the scheduler node, so a later caller announcing the same text is served the first one's result rather than running the target again — across projects *and* across MSBuild worker processes. That last part is the requirement, not a bonus: each inner build of a multi-targeted project runs in a process of its own, so neither a static nor `IBuildEngine4.RegisterTaskObject` (whose object cache is per node) can see the others. Projects rendering *different* text still announce separately, which is correct — they name different files to fix.

Consequences worth knowing:

- The announce run logs the error, so it is the run that returns false; the deferred verify run returns `true` even when verification failed, and the failing `<MSBuild>` call is what fails the consumer project. MSBuild requires the task that returns false to be the one that logged an error, so don't "fix" that return value.
- The message travels base64 (`DeferredDiagnostic.Encode`). It becomes a value in the `<MSBuild>` task's `Properties` list, which is both split on `;` and property-expanded, so a `;` or a literal `$(...)`/`@(...)`/`%(...)` in the body — an author's `MessageOverride` is free text — would otherwise be truncated or substituted away in transit.
- `NoWarn`, `MSBuildWarningsAsMessages`, `MSBuildWarningsAsErrors` and `MSBuildTreatWarningsAsErrors` are forwarded into the announce build **for a warning only**. MSBuild applies warning suppression from the project that *logs* the warning, so without them a consumer's `<NoWarn>SC005</NoWarn>` would silently stop working. They are part of the cache key, so projects that suppress differently announce separately — which is right for a warning and wrong for anything else: they act on nothing but warnings, and forwarding them with a message announced one identical SC029 per distinct `NoWarn` in the solution. The severity condition on the second `ItemGroup` in the announce block is what prevents that.
- The severity and importance arrive already resolved against the consumer's log levels (`_SponsorCheck_AnnounceSeverity` / `_SponsorCheck_AnnounceImportance`), so the announce build reads no consumer property of its own — see "Consumer log levels".
- `RemoveProperties` drops the globals MSBuild varies per project instance (`TargetFramework`, `RuntimeIdentifier`, `Configuration`, `Platform`). One left in splits the key and announces twice.
- The announce build evaluates the verifier targets as a standalone project — no SDK, none of a real project's properties — so the `__SC_INNER_IMPORT__` of an author's own targets is skipped there via `'$(_SponsorCheck_AnnounceCode)' == ''`. Announcing needs nothing from it, and evaluating someone else's build logic outside a real project is a failure mode not worth introducing.

Regression coverage: `ConsumerBuildTests.RepeatedDiagnostic_AcrossTargetFrameworks_IsAnnouncedOnce` and `_AcrossProjects_IsAnnouncedOnce` (each reports 2 announcements if the deferral is switched off; the second's two projects set different `NoWarn`, so it also reports 2 if the warning settings are forwarded with a message), `IgnoredLicense_NoWarnSC005_SuppressesTheWarning` (the other side: a warning still carries them), plus `VerifySponsorshipTaskTests.DeferDiagnostic_HandsTheDiagnosticBackInsteadOfLogging`, `Announce_ReplaysWhatTheDeferredRunCaptured` (asserts the announced text is byte-identical to the immediate path's) and `Announce_MessageSeverity_KeepsTheBuildGreen`.

## Multi-targeting in `SponsorCheck`

`SponsorCheck.csproj` is a single multi-targeted project (`netstandard2.0;net472`) that holds both the task code and the package metadata. `IncludeBuildOutput=false` keeps the build output out of `lib/`; a custom `_SponsorCheck_PackTaskDlls` target copies each TFM's DLL closure into `tasks/{tfm}/`. Both TFMs must build because the consumer's MSBuild may be either Core (.NET) or Framework (Visual Studio / MSBuild.exe). The `Microsoft.Build.*` pin in `src/Directory.Packages.props` is deliberately an old line rather than the newest available — the comment there says why, and it also gates whether `SponsorCheck.Tests` can run at all. `SponsorCheck.targets` and the generated verifier targets pick the right TFM via `'$(MSBuildRuntimeType)' == 'Core'` conditionals. Task classes live in the global namespace, so `UsingTask` references them by unqualified name (`BundleSponsorListTask` author-side, `VerifySponsorshipTask_<version>` consumer-side); the shipping assembly is `SponsorCheck.dll`. `BundleSponsorListTask` keeps a bare name because a project can only reference one SponsorCheck version, so it can't collide the way the verifier could.

The Tests project references the netstandard2.0 build via `SetTargetFramework="TargetFramework=netstandard2.0"`.

## The task assembly is trimmed

`SponsorCheck.csproj` references [Squash](https://github.com/SimonCropp/Squash), which runs the IL linker over each Release build of `SponsorCheck.dll` and removes what nothing reaches. Every package that bundles SponsorCheck carries a copy of that assembly per target framework, so its size is paid by every consumer of every such package. What goes is the Polyfill source compiled into it: about 660 KB down to about 220 KB per framework, and the `tasks/` folders a package carries from 4.1 MB to 3.3 MB. The rest of those folders is System.Text.Json and its dependencies, which Squash does not touch — it trims the one assembly.

Consequences worth knowing:

- **Nothing here may hand `JsonSerializer` a type of its own.** The linker follows code, not reflection. The two GraphQL request bodies used to be an anonymous type passed to `JsonSerializer.Serialize`; nothing in IL calls that type's getters, so they were removed, the request went out as `{}`, and GitHub answered "A query attribute must be specified". `GraphQlPayload` writes the body with `Utf8JsonWriter` instead, and `MessageOverrideFile` reads and writes its file with `JsonDocument`/`Utf8JsonWriter` for the same reason. Both produce byte for byte what the serializer did, and tests compare against the serializer to pin that.
- **IL2026 is left as the error it is.** The linker raises it at every `JsonSerializer` call, and `TreatWarningsAsErrors` fails the build. Don't add it to `NoWarn`: with it suppressed the build is green and the fetch is broken.
- **The tests run against the trimmed assembly**, because the test project references the Release netstandard2.0 build. That is what makes `GitHubSponsorsPlatformTests.FetchSponsorAccounts_SendsTheQueryAndTheLogin` and the Open Collective tests that read the captured request body real guards: with the anonymous type put back (and IL2026 suppressed) the first fails, as does `LiveLookup`. A Debug build is not trimmed.
- All of SponsorCheck's own types are public and in the global namespace, so they are roots and stay whole; `obj/Release/<tfm>/Squash/removed.txt` should list Polyfill and compiler-generated leftovers only. Read it after adding anything internal that is reached by reflection or by name.
- Squash needs a .NET 11 runtime on the build machine, which the SDK this repo already builds with includes.

## Token resolution precedence

In `BundleSponsorListTask.TokenFor`:

1. Explicit task property (`GitHubToken`, `OpenCollectiveToken`, `PolarToken`) — comes from MSBuild properties of the same name. MSBuild auto-imports env vars as properties of the same name (case-insensitive but underscore-sensitive), so a `GitHubToken` env var lands as `$(GitHubToken)` automatically. Conventional CI names like `GITHUB_TOKEN` / `POLAR_API_KEY` do **not** auto-flow — the env var must be named to match the property exactly.
2. User-secrets at key `SponsorCheck:<Platform>Token`. The UserSecretsId is read from `$(UserSecretsId)` in the **author's** csproj, not this repo.

`UserSecretsReader` reads the conventional path (`%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json` on Windows; `~/.microsoft/usersecrets/<id>/secrets.json` on Unix) and flattens nested JSON into colon-keyed paths.

## The platform fetch is shared across a build

The bundler runs in every packable project, and each used to call the platform API itself: a repo of twenty packages asked the same question twenty times per pack (a GitHub fetch measured about 1.6 s), all drawn from the one rate-limit budget SC108's note describes. Now `_SponsorCheck_BundleSponsorList` `<MSBuild>`-calls `_SponsorCheck_FetchSponsorList` **in SponsorCheck.targets itself**, passing the platform accounts as global properties, and hands what comes back to `BundleSponsorListTask` as `SharedFetch`. The target runs `FetchSponsorListTask`, which returns one item per platform.

The dedupe is the same one the verifier's announce call relies on: MSBuild caches a build result per (project path, global properties, targets) in the scheduler node, so the first project's call runs the fetch and every other project is served its result, across projects and across worker processes. Packing happens on whichever node built the project, so a static or `RegisterTaskObject` could not see the others.

Consequences worth knowing:

- **The tokens are not passed to the call.** The `<MSBuild>` task prints every property it is handed ("Global Properties:") at detailed verbosity, wherever the value came from. So the fetch reads the tokens the way the bundle target does, from `$(GitHubToken)` and friends, which reach a build of the targets file from the environment or from the build's own global properties (a call inherits those), plus user-secrets through the `UserSecretsId` that *is* passed. (MSBuild itself prints a value it expands from the environment, at the same verbosity, and did before this; a token set in a project file is printed by nothing, and passing it would start.)
- **A token set in a project file is the case that cannot share.** The fetch never sees it. So a result carries a fingerprint of the candidate tokens it was fetched with (`SharedFetchResult.Fingerprint`, a truncated SHA-256 over the ordered candidates), and the bundler takes a result only when its own candidates give the same one, for the same platform and account. Otherwise it fetches for itself, which is exactly what it does with no shared result at all. A mismatch therefore costs a call and can never change what is bundled; the bundler says so at low importance, because nothing else shows it.
- **A failure is shared too, and is not reported where it happened.** `FetchSponsorListTask` never fails and never logs an error or warning: the same account asked with the same credentials fails the same way, so the failure travels back as a result and each project reports it, with the code its own fetch would have raised. `SharedFetchFailure` keeps the exception's kind for that reason — the bundler maps the type to SC102, SC107, SC108 or SC100 — and anything that was not a platform error (a dropped connection) comes back as `SharedFetchException`, logged by message as before. An exhausted rate limit is now one refused call, not one per project.
- **The call targets the `build\` copy of the file, always.** SponsorCheck.targets also ships under `buildMultiTargeting\`, which is what a multi-targeted project imports for the outer build it packs from. `$(MSBuildThisFileFullPath)` would give the two kinds of project a fetch each (`_SponsorCheck_FetchProject`).
- **Free text travels base64**, as the deferred diagnostic does, but for a different reason: item metadata is an escaped string to MSBuild, so an account or a platform's error text containing `%41` would come back changed.
- `RemoveProperties` drops the globals MSBuild varies per project instance, as in the announce call. One left in splits the key and fetches again.
- The accounts passed are the unmerged PackageReference-or-PackageVersion values. The bundler still does the real merge (and raises on a conflict), and only takes a result fetched for the account it resolved.
- An override list is a file read, so the call is skipped for it and a shared result is never consulted.
- The lines the fetch logs (`GitHub Sponsors: fetched N sponsors`, the private-sponsor count) now appear once per build, under SponsorCheck.targets, rather than once per project. `SponsorFetch.WithCandidateTokens` is the fetch both tasks run, so the try-each-candidate behaviour is the same on either path.

Regression coverage: `AuthorPackTests.SharedFetch_SeveralPackagesInOneBuild_FetchOnce` packs the `_Shared/SharedFetch` solution (two single-targeted packages and a multi-targeted one) with no token, so the fetch fails before making a request and the suite stays off the network. It counts the line `FetchSponsorListTask` logs each time it runs (1) and the line the bundler logs when what it reports is the shared failure (3), in a detailed log. Pointing the call at `$(MSBuildThisFileFullPath)` makes the first count 2; dropping `SharedFetch` from the bundler call makes the second 0. `SharedFetch_DoesNotHandTheTokensToTheCall` passes a token through the environment and asserts it is not among the printed properties, and `SharedFetch_NotAskedForWithAnOverrideList` that an override list starts no fetch. `SharedFetchResultTests` covers the round trip through an item, the fingerprint and each failure kind; `FetchSponsorListTaskTests` that a failure is handed back and not reported; and the `BundleSponsorListTaskTests.SharedFetch_*` block that the bundler takes its own result, sets aside one fetched with other credentials or for another account or platform, and reports a shared failure under its own code. None of those reaches a platform. A successful shared fetch end to end needs the live API, so it is not in the suite: after changing this, pack a solution of several packages with a real token at `-v:normal` and count the `fetched N sponsors` lines.

## SponsorshipStart bypass

A consumer who began sponsoring after a package's pack date can't possibly be in the bundled hash list. `SponsorshipStart="yyyy-MM-dd"` lets them attest to a start date. If `SponsorshipStart > PackDate`, the verifier skips the hash check and emits a high-priority build message naming the unverified sponsor (audit trail in the consumer's own log). Future `SponsorshipStart` fails with `SC015`.

This is why `OutputPackDatePath` exists in the bundler and `PackDatePath` is plumbed all the way to `DecisionApplier.Apply`.

## Integration test isolation

`ThePackageBuilder` (one-time setup) packs `IntegrationTests/Fixtures/_Shared/ThePackage` once per suite with `SponsorListOverride=Fixtures/sponsors-override.json` and `SponsorCheck_PackDateOverride=2024-01-01` into a per-suite local feed under `Path.GetTempPath()/sponsorcheck-it-feed/<guid>`. Consumer fixtures get a generated `nuget.config` pointing at that feed.

`ConsumerBuildTests.BuildFixture` writes empty `Directory.Build.props` / `Directory.Build.targets` into each fixture's temp dir so the parent `IntegrationTests/` config (CPM, etc.) doesn't leak in. It also uses an isolated `--packages` dir under the work dir to avoid the global NuGet cache caching a stale `SponsorCheck.0.1.0` between runs.

The 2024-01-01 backdate is what enables `Consumer.RecentSponsor` to test the `SponsorshipStart > PackDate` bypass against today's clock.

## Private sponsors are never bundled

A sponsorship that is private on GitHub Sponsors, or incognito on Open Collective, is filtered out before hashing:

- `GitHubSponsorsPlatform` keeps `includePrivate: true` on both connections and selects `privacyLevel`, then drops `PRIVATE` entries in the two accumulation loops. `includePrivate: false` would filter server-side and is deliberately *not* used — asking for them is what makes the excluded count knowable, so the pack log can tell the author how many sponsors now need the attestation route.
- `OpenCollectivePlatform` selects `isIncognito` through an `... on Individual` inline fragment (the field is on `Individual`, not on the `Account` interface the member's `account` field is typed as) and drops those members. Validate any change to that selection set against the live API before anything else — Open Collective answers an invalid selection set with `GRAPHQL_VALIDATION_FAILED`, which is exactly what the comment atop the file records happening with `role: [SPONSOR]`.
- Both read an *explicit* positive value only. Absent or unrecognized has to read as public/visible: `isIncognito` is absent for every non-Individual member (organisations, collectives, funds), and treating "unknown" as private would empty the whole list if GitHub ever renamed `privacyLevel`.
- `ISponsorshipPlatform` still returns `IReadOnlyList<string>`; the filtering happens inside each implementation, and each logs its own count via `PrivateSponsorAdvice`. Never log the accounts — the entire point is that those identities don't leave the author's machine.
- `SponsorListOverride` is unchanged and unfiltered. It is an explicit list, so excluding someone is the author's job; this also keeps `AuthorPackTests.BundledHashesMatchOverrideListAndAreDeterministic` (hard-asserts 4 lines) intact.

**The consumer's route.** `SponsorshipPrivateUntil="yyyy-MM"` alongside a `<Platform>SponsorAccount` skips the hash check and emits SC059, a high-priority message (like SC017, so a paying sponsor isn't warned on every build for the whole term). It is a *qualifier, not a mode* — same rule as `SponsorshipStart` and `SponsorshipExemptionUntil`, so on its own it still yields MissingConfig/SC001. Checked **before** `SponsorshipStart` in `ApplySponsor`: a valid claim decides the build outright, and checking it first is what makes an expired claim fail loudly (SC056) instead of silently degrading into the start-date path when a consumer set both.

The end month is the whole mechanism. Nothing about a private sponsorship is checkable, so unlike `SponsorshipStart` — which self-expires when a newer pack date overtakes it — the declaration would otherwise never be re-examined. This is not a weakening of enforcement: `SponsorshipLicenseIgnored="true"` was already the universal bypass. That is also why there is deliberately **no** author switch to disable the route — blocking it adds no enforcement while breaking the one honest path a paying private sponsor has.

**The cap rides in the generated targets, not a sidecar.** `PrivateSponsorMaxTermMonths` (author metadata, default 12, validated to SC109) is substituted into both verifier templates via the `>__SC_PRIVATE_MAX_MONTHS_RAW__<` element-content placeholder — the same regex-anchored mechanism as `>__SC_OWNER_ID_RAW__<`. A sidecar would have cost an `Output*Path`, a `<None>` pack item, a reader/writer, a `NupkgParser` const and an `AuthorPackTests` pair, for one integer. `VerifySponsorshipTask.ResolvePrivateSponsorMaxTermMonths` falls back to the default on a missing or malformed value rather than failing: it comes from the publisher's packed targets, so the consumer can't fix it, and packages published before the cap existed carry no such property.

**Why the SC007/SC008/SC024 body gained a private-sponsor hint.** A pre-existing private sponsor upgrading to a newly packed version loses their bundled hash and lands there with nothing wrong on their side — `SponsorshipStart` can't help, since it only bypasses when `start > packDate`. The hint is their only signpost. It names the cap as a duration ("at most 12 months out") rather than rendering `today + N`: that message is otherwise clock-independent, and baking a computed month into it would churn every SC007 snapshot monthly.

Regression coverage: `GitHubSponsorsPlatformTests.FetchSponsorAccounts_ExcludesPrivateSponsorsAndReportsTheCount` / `_LapsedPrivateSponsor_CountedOnce`, `OpenCollectivePlatformTests.FetchSponsorAccounts_RequestsIsIncognitoAndReportsExcludedCount`, the `VerifySponsorshipTaskTests.PrivateSponsor_*` block (fixed clock, and every fixture claims an account absent from the hash list so a pass proves the check was skipped rather than satisfied), `AuthorPackTests.PrivateSponsorMaxTermMonths_*`, and `ConsumerBuildTests.PrivateSponsor_PublisherNarrowedCap_FailsWithSC053` (9 months out is inside the 12-month default and outside the fixture's cap of 6, so it only passes if the cap actually reached the consumer's verifier).

## Diagnostic code conventions

- `SC0xx` — consumer-side (verifier). 001-007 are license-mode errors; 008 is the `SponsorshipStart` trust-attestation info message; 009 is corrupt install; 010-011 are `SponsorshipStart` errors.
- `SC1xx` — author-side (bundler). 100 = catch-all for `MaintenanceFeeException` (HTTP/GraphQL errors); 101 = no platform metadata; 102 = required platform credential missing (typed via `MissingCredentialException`); 103 = user-secrets read warning.

**Message-severity codes are high importance only on a build server.** SC017, SC029/SC030/SC031 and SC059 are the audit trail — which carve-out was claimed, or that an unverifiable attestation was trusted — so `SponsorCheckLog.EmitRendered` logs them at `MessageImportance.High` when `BuildServerDetector.Detected` and `Low` otherwise. The CI log keeps the record at default verbosity; a local build stays quiet and `-v detailed` brings it back. Errors and warnings are untouched.

That is only the default: a consumer's `SponsorCheckMessageLevel` replaces it (see "Consumer log levels" below). The seam is `SponsorCheckLog.DefaultImportance(onBuildServer)`, reached through `LogLevels.Apply(severity, onBuildServer)` — the same shape as `TokenSetupAdvice.MissingTokenMessage`, because the detector reads the environment once into a static and tests must pin the input rather than flip real CI variables. Two test-side consequences: `ModuleInitializer` ignores `BuildMessageEventArgs.Importance` in snapshots (High is the enum default so it was never recorded before, and recording Low would make every message snapshot disagree between CI and a developer machine — `SponsorCheckLogTests` pins both branches directly instead), and `DotnetCliRunner.PinBuildServerDetection` scrubs every variable the detector reads out of each fixture build's environment, setting `JENKINS_URL` when the fixture wants build-server behaviour. Worth knowing: the detector counts Docker and WSL as build servers, so a devcontainer gets the CI treatment.

Regression coverage: `SponsorCheckLogTests.MessageDiagnostic_OnBuildServer_IsHighImportance` / `_LocalDev_IsLowImportance` / `ErrorAndWarning_AreUnaffectedByTheBuildServerFlag`, and `ConsumerBuildTests.MessageDiagnostic_OffBuildServer_StaysOutOfTheDefaultLog` (the same fixture that asserts SC029 is present on a build server, asserting it is absent off one).

**They are also one line of log.** `SponsorCheckLog.Wrap` puts the See link on the body's own line for a message whose body is a single line; errors, warnings and multi-line bodies keep it after a blank line. The console logger repeats the file, code and project on every line of a multi-line message, so the blank separator plus a link line made each audit record three lines, the middle one empty — which is what the PR #36 thread reported, and which reads like a dedupe failure but isn't one. The multi-line exception exists because a publisher can downgrade SC009 to a message, and its body ends in a sponsor URL that the docs link would otherwise run on after. Because the rendered text is the dedupe key, changing the wrap changes nothing about once-per-build; and because the seven message snapshots dropped below `Inline(maxLines: 10)` with it, they are now inline `.Snapshot(...)` literals in `VerifySponsorshipTaskTests`. Regression coverage: `SponsorCheckLogTests.MessageDiagnostic_KeepsTheLinkOnItsLine` / `MultiLineMessageBody_KeepsTheLinkApart` / `ErrorAndWarning_KeepTheLinkOnItsOwnLine`, and `ConsumerBuildTests.NonCpmExemption_BuildsWithSC029Message`, which counts the lines carrying the code in a real build's output.

Any time a code is added, removed, or its message text changes, update the per-code section in `docs/VerifierDiagnosticCodes.md` (SC0xx) or `docs/BundlerDiagnosticCodes.md` (SC1xx) alongside `VerifySponsorshipTask`/`BundleSponsorListTask`. The Syntax line must mirror the actual interpolated format string and the Example must be a plausible rendering — these double as the public reference and as a reviewer cross-check.

## Consumer log levels

`SponsorCheckMessageLevel` and `SponsorCheckWarningLevel` let a consumer choose how SponsorCheck's messages and warnings are logged: `warning` logs a warning, `high`/`normal`/`low` log a message at that importance. They are global and unprefixed (like the author-side `SponsorCheckBundleInPullRequest`), so one setting in `Directory.Build.props`, a project or the environment covers every SponsorCheck package in the build — a consumer of Verify doesn't need to know Verify's owner id. Unset keeps the defaults (a message is high on a build server and low elsewhere, a warning stays a warning). Errors are never remapped: they are the enforcement, and lowering a warning grants nothing `NoWarn` didn't already. Author severity overrides apply first, so a code a publisher downgraded to a warning answers to the warning level.

Things worth knowing:

- **The verify run resolves; the announce run only logs.** `VerifySponsorshipTask` now renders into `CapturingBuildEngine` on the immediate path as well as the deferred one, then applies `LogLevels.Apply` to the one captured diagnostic in a single place. The deferred path hands back the resolved `DiagnosticSeverity` plus a `DiagnosticImportance` (set for a message only), the templates forward it as `_SponsorCheck_AnnounceImportance`, and the announce run logs at what it is handed — so the announce build needs neither consumer property. The importance joins the cache key, which only splits announcements between consumers that asked for different levels. Since the resolved severity is what the announce block's `== 'warning'` condition sees, a message raised to a warning gets `NoWarn` forwarded and a warning lowered to a message doesn't, both correctly.
- **Levels are applied after rendering.** The text, and so the one-line wrap, is decided by the diagnostic's own severity; the level only changes how it is logged. A raised audit message stays one line; a lowered SC005 keeps its remediation block.
- **An invalid value is SC060, checked before verifying.** Strict like SC011/SC041/SC050, because a typo in a logging preference is otherwise invisible on a quiet build. It is reported *instead of* the verification result (like SC020), which keeps the one-diagnostic-per-run invariant `CapturingBuildEngine` relies on.
- **The vocabulary is closed.** Every SponsorCheck version in a build reads the same two properties, and each rejects values it doesn't know — so a level added later (a `none`, say) would fail the build of any consumer that also references a package bundling an older SponsorCheck. Adding one needs a different answer for unknown values first.
- A package bundling an earlier SponsorCheck ignores both properties.

Regression coverage: `LogLevelsTests` (parsing and the full mapping), `VerifySponsorshipTaskTests.MessageLevel_*` / `WarningLevel_Normal_LowersSC005ToAMessage` / `LogLevels_LeaveErrorsAlone` / `InvalidLogLevel_FailsWithSC060BeforeVerifying` / `DeferDiagnostic_HandsBackTheResolvedSeverityAndImportance` / `Announce_LogsAtTheImportanceItIsHanded`, and `ConsumerBuildTests.MessageLevel_Low_KeepsTheAuditMessageOutOfTheCiLog`, `WarningLevel_Normal_LowersSC005BelowTheDefaultLog`, `OwnerMode_MessageLevelHigh_ShowsTheAuditMessageOffABuildServer` (the owner template wires the properties separately, and this raises above the local default rather than lowering) and `InvalidLogLevel_FailsWithSC060`. The fixtures behind the first two are the snippets in `docs/ConsumerUsage.md#log-levels`.

## Project-reference coverage (dropping redundant transitive diagnostics)

A package with `CheckTransitiveReferences="true"` ships its verifier under `buildTransitive/`, so NuGet imports it into every transitive consumer in the closure. In a multi-project solution where the direct `<PackageReference>` lives in one project (call it Lib) and other projects only reach the package through `<ProjectReference Include="Lib\Lib.csproj" />`, the verifier *also* fires in those downstream projects — emitting duplicate SC0xx errors for what is logically one verification.

Both `ConsumerVerifier.targets` and `ConsumerVerifierOwner.targets` define two companion targets per package — `_SponsorCheck_CoversDeep_<sanitized-id>` and `_SponsorCheck_CoversShallow_<sanitized-id>` — alongside the verifier target. The verifier runs `VerifySponsorshipTask` first — deferred, so nothing is logged yet — and only if that hands back a *rejection* does it `<MSBuild>`-call the deep responder on every `@(ProjectReference)`. Each responder checks the called project's `@(PackageReference)` for ThePackageId; the deep one also walks that project's own `@(ProjectReference)` via the shallow responder. That gives depth-2 visibility (self, direct ref, ref-of-ref) — the common solution layout. If any project reports coverage, the announce call is skipped via Condition and the diagnostic is dropped. The `_SponsorCheck_OwnerVerified_<owner>` flag is set either way so other owner-mode packages in the same project don't re-verify.

**Verify first, walk second — don't put the walk back in front (issue #45).** Coverage exists only to suppress a redundant diagnostic, so a project with nothing to announce has nothing to ask. The walk used to run before the task, unconditionally, and that cost every consumer on every build: each responder call does trivial work, but MSBuild has to run it on the node that owns the referenced project, and late in a large build those nodes are busy compiling, so the calling project sits blocked inside the `<MSBuild>` task until each request gets a turn. The report measured 173 seconds of that across the 11 projects consuming one package in a 700-project solution, with a valid sponsorship declared. `SkipNonexistentTargets="true"` does not help with this — it keeps the call from failing when a reference doesn't define the responder (e.g. it doesn't transitively reference ThePackage at all), but the request is still scheduled on that project's node.

**An accepted claim doesn't walk either.** "Has a diagnostic" was not a tight enough test: an exemption, a private or recent sponsorship and an ignored license each log on *every* build (SC029–SC031, SC059, SC017, SC005/SC006/SC023), so those consumers kept paying the walk on every build. None of those is a rejection. Coverage is for a project with no acceptable declaration of its own, leaning on a referenced project that has one; a project whose declaration was accepted has nothing to be covered for. So the task hands back `DiagnosticAcceptedClaim`, and both templates skip the walk when it is true.

What counts as accepted is decided where each diagnostic's default severity is declared, not in a list of codes: `SponsorCheckLog.HighMessage` (every message-severity code is an audit record) and `SponsorCheckLog.Emit` when the default severity is not Error *and* the severity after the publisher's overrides is not Error either. Both halves are load-bearing. A publisher who downgrades SC001 to a warning has not given a transitive project a declaration, so that stays a rejection and coverage still suppresses it — drop the default-severity half and every covered project announces that warning. A publisher who raises SC005 to an error has turned the claim into a rejection, which coverage was always allowed to suppress — drop the other half and a covered project that used to build starts failing. The marker reaches the task as the captured event's help keyword (`SponsorCheckLog.AcceptedClaimKeyword`), for the same reason `CapturingBuildEngine` exists at all: an event is the only thing that crosses from `DecisionApplier` and the renderers below it without threading a sink through them. It never reaches a build log — the task replays the capture through `EmitRendered`, which sets no keyword — and `HelpKeyword` was already ignored in snapshots. A consumer's log levels don't change it: they decide how a diagnostic is logged, not what it is.

One visible consequence: a project that makes an accepted claim of its own now reports it itself even when a referenced project also references the package, where it used to be dropped as covered. For the audit messages, and for any diagnostic in owner mode or under CPM, the text is the same in every project and the announce call still reports it once. The exception is SC005 without CPM, whose text names the project file: two projects that each set `SponsorshipLicenseIgnored="true"` on their own `<PackageReference>` are now each warned (`IgnoredLicense_InAProjectAndItsReference_WarnsForEach`).

The coverage path only matters when `CheckTransitiveReferences="true"` — without it, NuGet doesn't import the verifier into transitive consumers in the first place, so there's nothing to skip.

Important nuance the user explicitly scoped: **`CheckTransitiveReferences` semantics for NuGet transitive references are unchanged** — a consumer that pulls ThePackage in via a transitive *package* dependency still gets the verifier and still has to supply metadata. The skip-on-coverage logic only fires when the coverage is reachable via a `<ProjectReference>` (i.e. same solution).

The responders use `$(_SponsorCheck_ThePackageId)` (a property set from the `>__SC_PACKAGE_ID_RAW__<` element substitution) inside attribute values, because the bundler's `__SC_PACKAGE_ID_RAW__` substitution at `BundleSponsorListTask.cs:142` is regex-anchored to `>...<` element content and won't touch attribute strings. If you ever need the raw id in an attribute, route it through the property — don't expand the substitution to attribute syntax.

Regression coverage: `ConsumerBuildTests.OwnerMode_ProjectReferenceCoverage_SkipsRedundantVerification` plus the fixture `Consumer.OwnerCoveredByProjectReference` (top-level with no PackageReference + no property; Lib subdir with the PackageReference + property). The author fixture `_Shared/ThePackageOwnerModeTransitive` is owner mode + `CheckTransitiveReferences="true"` — needed to exercise this path. `ProjectReferenceCoverage_SuppressesTheTransitiveDiagnostic` is the per-package counterpart (`_Shared/ThePackageTransitive`). `OwnerMode_ValidSponsor_DoesNotWalkProjectReferences` and `ValidSponsor_DoesNotWalkProjectReferences` pin the order: the same shapes with a valid declaration in the top-level project, asserting no responder target ran. `OwnerMode_AcceptedClaim_DoesNotWalkProjectReferences` and `AcceptedClaim_DoesNotWalkProjectReferences` do the same for an exemption claim, and also count the audit message (still one). All six build at `detailed` verbosity and look for the `_SponsorCheck_CoversDeep_` prefix in the log — a fixture can't hook the responder by name because the sanitized id ends in a hash, and `normal` verbosity doesn't show the call. The two covered tests assert the prefix *is* there, which is what keeps the absence assertions from passing vacuously; with the walk moved back in front, the two `ValidSponsor` tests fail, and against a package that walks for any diagnostic the two `AcceptedClaim` tests and the ignored-license one fail. `VerifySponsorshipTaskTests.DeferDiagnostic_MarksEveryKindOfAcceptedClaim` / `_ARejectionIsNotAnAcceptedClaim` / `_DowngradedRejection_IsStillARejection` / `_IgnoredLicenseRaisedToAnError_IsARejection` / `_ConsumerLogLevels_DoNotChangeWhatIsAccepted` pin what is marked, and `ImmediatePath_DoesNotLeakTheAcceptedClaimMarker` that the keyword stays out of a real log.

`IntegrationTests/Benchmarks` measures all of this in a generated solution — see `contributing.md#benchmark`. It reports the time spent inside the verifier's target summed over the consuming projects, which is the number the issue reported and the one that moves; overall build time barely does, because a project blocked in an `<MSBuild>` call hands its node back. Don't judge a change to the verifier targets by wall-clock alone.

## MSBuild task batching trap

`SponsorCheck.targets` and `ConsumerVerifier.targets` flatten item-metadata into scalar properties (`@(Items->'%(M)')`) before passing to the bundler/verifier task. Do not revert this to direct `%(ItemGroup.Metadata)` task parameters. With CPM both `@(PackageReference)` and `@(PackageVersion)` carry SponsorCheck items, and direct metadata accessors cause MSBuild to invoke the task once per ItemGroup batch. The PackageReference batch typically has no metadata under CPM (it lives on PackageVersion), so that batch fires SC101/SC001 even though the other one would succeed. Regression coverage: `AuthorPackTests.CpmMultiTargeted_MetadataOnPackageVersion_BundlesSuccessfully` (bundler) and `ConsumerBuildTests.CpmConsumer_LicenseMetadataOnPackageVersion_PassesWithoutBatchingError` (verifier).

## Configuration gating

The bundler target is gated on `'$(Configuration)' == 'Release'` (it only runs alongside packing). The consumer verifier runs in every configuration — Debug builds enforce sponsorship too. Don't reintroduce a `Configuration == 'Release'` gate on the verifier.

## Code style

- File-scoped namespaces, `LangVersion=preview`, nullable enabled, `TreatWarningsAsErrors=true`, `EnforceCodeStyleInBuild=true` (see `src/Directory.Build.props`).
- Tests use TUnit + Verify. `StubBuildEngine` and `TaskLoggingHelperFor` (in `VerifySponsorshipTaskTests.cs`) are the standard test plumbing for invoking tasks directly.
- Live tests that need credentials use `LiveTokenResolver.ResolveOrSkip(envVar, secretKey, label, extra?)` — env var → user-secrets → `Skip.Test`. Skip messages flip between user-secrets-first (local) and env-var-only (CI) advice based on `BuildServerDetector.Detected`. The bundler's missing-credential errors (`SC102`) flip the same way via `TokenSetupAdvice.MissingTokenMessage`.
- `src/SponsorCheck/BuildServerDetector.cs` is a verbatim duplicate of `VerifyTests/DiffEngine/src/DiffEngine/BuildServerDetector.cs`. If the upstream changes meaningfully, re-sync this copy rather than editing in place.

## readme and docs pages are generated

`readme.md` and the pages under `docs/` use [MarkdownSnippets](https://github.com/SimonCropp/MarkdownSnippets) (via `MarkdownSnippets.MsBuild` referenced from `src/SponsorCheck.Tests`). Edits inside snippet/include blocks get clobbered on the next test build — edit the source file (e.g. an integration fixture csproj, or `docs/*.include.md`), not the expanded block.

Doc structure: `readme.md` is a deliberately short landing page split by audience — consumers land in `docs/ConsumerUsage.md`, OSS authors in `docs/AuthorSetup.md`. Contributor-facing content (project layout, build/test instructions) lives in `contributing.md`.
